# Kimodo Transition Overlap (v0.20.0)

Select a **Kimodo** block and edit **Transition Overlap (30 FPS)** in its sidebar settings or double-click popup. The default is **5**. This is the incoming transition: for selected blocks A, B and C, B's setting controls A-to-B and C's setting controls B-to-C. Since v0.20.0, A also uses its overlap when an existing generated clip ends exactly at A's start. This includes selecting and generating only A.

Values are model frames at 30 FPS, independently of scene FPS. Five frames is about 0.167 seconds, ten is about 0.333 seconds, and fifteen is 0.5 seconds. On a 60 FPS scene, five model frames correspond to approximately ten scene frames. The input accepts 1–300. For an existing adjacent clip shorter than the requested overlap, the add-on uses its available frames and retains the block's setting. Within a selected Kimodo sequence, the incoming overlap must fit the preceding selected block. Larger values use a longer previous-motion context.

For an existing predecessor, the addon samples its native NLA tail at 30 Hz, including the user's correction layer, and sends those poses as a separate history payload. The worker encodes this tail into Kimodo's motion representation and seeds the official multi-prompt transition with it. The model sees the actual motion history, not just one ending pose. Explicit user Start keys remain pose constraints alongside the history. At least five samples are encoded for smoothing/velocity features, then only the requested tail is used, so 1–4 frame overlap settings are supported without short-history smoothing failures.

The returned history prefix is trimmed before applying the newly selected interval. Existing predecessor Actions/strips, user keys and timeline block bounds are preserved. Native NLA Blend In/Out remain unchanged. With no generated predecessor, or with a gap before the selected block, no history overlap is used; the existing held-ending-pose behavior still applies where available. A Kimodo run can use an adjacent MotionBricks clip's canonical SOMA history as well. MotionBricks generation itself keeps its fixed four-pose model context and exposes no equivalent overlap field.

The pinned official Kimodo API accepts one scalar overlap for a whole multi-prompt call. `runtime/kimodo_transitions.py` adapts its overlap assignment and optional initial motion list in memory on the current worker instance. All official cropping, transition constraints, postprocessing and raw blending paths remain in use. Checked assignment matches fail clearly if the upstream sequence implementation changes. The original bound method is restored after success or failure; upstream engine files are not edited. Requests lacking the per-block overlap field retain the default of 5; requests with no history payload retain the previous unseeded sequence behavior. Settings changed during generation invalidate that block's result or stop pending submission rather than applying an obsolete transition.

## Validation

- `results/blender_bridge/transition_overlap.json` exercises real Blender RNA, Kimodo-only sidebar/popup visibility, stored defaults, distinct values, bounds, stale settings and save/reopen in a separate background process.
- `results/blender_bridge/previous_kimodo_context.json` verifies exact native tail sampling, state restoration, an explicit user Start key, one-frame feature support, oversize/gap/selected-predecessor handling and payload validation.
- `results/blender_bridge/previous_kimodo_generation.json` exercises actual external-history overlap with user corrections, predecessor/source-key preservation, raw and postprocessed paths, minimum/full-tail lengths and a multi-block selection seeded by an existing clip.
- `results/blender_bridge/mixed_generation.json` also passes after the update: the final Kimodo run receives five actual context frames from the preceding MotionBricks result while preserving source keys and native boundary poses.
- `results/blender_bridge/transition_generation.json` records actual model input context lengths for a three-block sequence configured as 42/7/13: **0/7/13** with postprocessing enabled and disabled. Its current single-block case uses the existing thirteen-frame history. A saved pre-feature request with no history payload replays with default 5 against its original output.

These are numerical and background API checks. Motion quality for arbitrary prompts and manual UI acceptance remain separate from successful execution. No user GUI was automated.
