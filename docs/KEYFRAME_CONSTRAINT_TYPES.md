# Native keyframe constraint types (v0.28.1)

Pose the SOMA bones and insert ordinary Blender pose keys. Right-click the diamond in the dedicated Motion Timeline's **Keyframes** row, select the desired goals in the **Pose Constraint Types** dialog and confirm with **OK**. Multiple hand, foot and root goals can remain selected together. Editing targets the clicked key and does not move the playhead; cancel leaves its annotation unchanged. Since v0.28.1 the playhead-dependent sidebar selector has been removed, so moving through keyed frames does not insert/remove that panel or shift the generation controls. Existing key annotations and generation behavior are retained.

## Object constraints

Move the playhead in the Motion Timeline and choose **Constraint → Add Constraint**. Click a square marker in the **Constraints** row to show all object constraints at that frame in the right sidebar. Select a list entry to edit its **Constraint Type**, **Target Object**, or **Frame**. Drag the marker to retime the selected constraint. Press **X** or **Delete** over the timeline to remove it.

Kimodo and ARDY sample the target object's evaluated transform at the marker frame, including its parent and animation. A hand or foot target uses the object's origin for the wrist or ankle and aligns the bone's axes to the object's axes. A root target uses the origin's ground position. **Constrain Root Heading** uses the object's local −Y direction, and **Constrain Root Height** uses its height as a soft hips-height goal. A root marker takes precedence over the Path Curve at that sample. **Show Pose Targets** previews the goals sent to the model.

Markers belong to the selected SOMA actor and require no Blender pose keys. Native pose keys and object markers can supply different goals in the same block. At the same frame, the object takes precedence over a native key of the same partial type. A Full Body key needs its own model sample. MotionBricks uses native Full Body pose keys.

## Native pose constraint types

| Label | Type | Generation target |
|---|---|---|
| FB | Full Body | The complete composed body pose; default for all unannotated keys |
| LH | Left Hand | Left-hand position and orientation |
| RH | Right Hand | Right-hand position and orientation |
| LF | Left Foot | Left-foot position and orientation |
| RF | Right Foot | Right-foot position and orientation |
| R2 | Root Position (2D) | Root ground-plane position |
| R2H | Root Position (2D) + Constrain Root Heading | Root ground-plane position and keyed facing direction |
| R3 | Root Position (2D) + Constrain Root Height | Root ground-plane position and keyed hips height |
| R3H | Root Position (2D) + both options | Root ground-plane position, keyed hips height and facing direction |

## Optional root height

For Kimodo and ARDY, right-click a native key diamond, select **Root Position (2D)** and enable **Constrain Root Height** in the dialog. It defaults off and can be combined independently with **Constrain Root Heading**. Without heading, the label becomes **R3**; enabling both shows **R3H**. Hand/foot combinations are retained, for example **LH+R3H**. Removing Root Position or choosing Full Body clears both options.

The height is the **composed visible hips position**, including the generated base and user correction, sampled at that native key. In Blender this is the vertical Z coordinate after the usual rig/object/unit conversion; the model uses Y-up coordinates. Move the hips vertically and key the pose to change it. The adapter sends the model's existing `root_y_pos` channel in addition to the ordinary root-plane condition and optional heading. Kimodo also needs the **Hips position**: its inverse decoder takes actual hips height from `local_joints_positions`, not the smooth-root height feature. That one joint is conditioned at the same root-plane position and keyed height. No other joints or rotation channels are added to the mask. Other body joints remain free to respond to the prompt and the selected goals.

A Path Curve continues to supply ground-plane positions, independently of keyed height. Curve elevation is ignored. This is a model conditioning goal rather than a hard height override: the stock root-plane postprocessing branch does not directly pin vertical position. Native NLA application preserves the generated partial-frame solution and counterbalances the existing user correction layer without adding a single-frame FK snap.

**Measured accuracy limitation:** independent height masks are an addon extension, not a stock Root2D control. In the standing-prompt fixture, requesting a 0.30 m hips drop at the middle key with the default Constraint Guidance of 2 left a large height error. Raising guidance improved some frames but also overshot or destabilized other heights. The addon retains the user's existing guidance setting and does not silently raise it. Height is therefore exposed as a **soft model goal**, not a precise pin; use a Full Body pose when the complete authored pose must take priority. The sidebar/dialog states this limitation, each result records `root_height_errors`, and automatic application reports the maximum deviation in centimeters. Numerical condition-mask/integration checks passing does not mean the separate 5 cm accuracy criterion passed.

With both models started from the same saved input, the middle target was 0.705185 m. Kimodo produced 0.969194 m (0.264010 m error, 30 steps); ARDY produced 0.995447 m (0.290263 m error, 10 steps). Both used BF16 text encoding, seed 0, guidance 2 and stock postprocessing. Native NLA replay matched the raw root positions within 0.000001 m, confirming that the large deviation was already in the model output. Both failed the separate 5 cm target-accuracy criterion. This fixture intentionally combines a standing prompt with a lower sparse height target; it establishes a real limitation, not accuracy for other motions.

**Repeated-generation limitation:** partial constraints read the current composed visible pose again on each submission. Although the original user key points remain in the correction Action, their original absolute height goal is not cached independently. A failed height result can therefore become the next target when generating again without restoring the raised visible pose. The supplied jump scene confirmed an initial 1.453 m target becoming about 1.021 m on the next generation. See [read-only scene/request diagnosis](JUMP_HEIGHT_DIAGNOSIS.md). This goal-preservation issue is distinct from model target accuracy.

Annotations `ROOT_HEIGHT` and `ROOT_HEADING_HEIGHT` retain existing Action-slot ownership and key move/delete/Undo/save behavior; old `ROOT` and `ROOT_HEADING` records are unchanged. Requests use the same `ROOT` kind with optional boolean `root_height`; the companion advertises the `root_height` capability. An older companion is rejected before submission. A bridge-local subclass preserves height through native Kimodo segment cropping/device transfers and ARDY window offsets, while retaining native Root2D postprocessor identity. Vendored model sources and weights are unchanged. Restart both Blender and the companion after updating.

## Optional root heading

For Kimodo and ARDY, right-click a native key diamond, select **Root Position (2D)** and enable **Constrain Root Heading** in the dialog. It is off by default. The facing direction comes from the composed visible pose's hip vector, using each model's native heading convention. Pose/rotate the character and insert a key to author that direction. This is a ground-plane facing goal, not a lock on root pitch, roll or height.

Position-only keys retain the **R2** label; heading-enabled keys without height show **R2H**, including combinations such as **LH+R2H**. With height enabled, these become R3/R3H. Removing R2 or selecting Full Body clears the heading option. A Path Curve continues to supply ground-plane positions while the keyed facing can point in a different direction from the curve tangent. Heading is a model condition; the stock postprocessor does not directly pin its angle, so an exact orientation match is not guaranteed. Applying partial constraints never adds a hard FK rotation override.

The option is stored with the native key's Action-slot annotation (`ROOT_HEADING`) and follows existing key move/delete/Undo/save behavior. Requests still use the ordinary `ROOT` kind, with `root_heading: true` only when enabled. Other targets and older position-only requests are unchanged. Kimodo receives cosine/sine pairs; ARDY receives radians as required by its native constraint API. Both frontend and companion must be updated. An older companion is rejected with a restart instruction rather than silently ignoring the option.

Labels appear in small theme-colored text beside the real native key diamonds, including combinations such as **LH+RH**, **LH+RF** and **LH+RH+LF+RF**. Labels are hidden when zoom leaves insufficient room for the complete label between neighboring keys; diamonds remain visible. No global Blender theme changes or extra animation channels are introduced.

Each native keyed frame can combine any of LH/RH/LF/RF/R2 in a Kimodo or ARDY block, alongside a Path Curve. For example, FB at frame 0, LH+RH at frame 20, LH+RF at frame 40 and FB at the end. **Full Body is exclusive**: selecting it clears partial goals, and selecting a partial goal clears FB. Deselecting the last partial goal returns to FB. A full-body pose already contains all of those body targets. The model's standard end-effector formulation also includes its native root/heading reference; a hand constraint is not a whole-arm rotation lock or an independent elbow target.

Generation reads the composed visible pose (generated base plus user correction layer), then passes its selected type to Kimodo/ARDY. When a root curve is active, hand/foot world-space targets are retained rather than translated with the curve; full-body/root targets retain the existing curve placement policy. Native user correction keys remain intact. Full Body retains exact authored local channels at its keyed frame. Partial types instead use the selected endpoint/root goal: the model may choose different shoulder, elbow or knee rotations. Since v0.22.1, applying a result does not forcibly restore those old local rotations at just the partial-target frame. The base counterbalances the existing correction layer throughout the generated interval to avoid applying that correction twice. New user edits after generation still combine normally. See [partial-target replay diagnosis](PARTIAL_CONSTRAINT_FK_POP_FIX.md).

Target values are generation constraints, not a guarantee of exact world-space pinning. In the ARDY curve fixture, the stock postprocessor's shared root reference produced up to about 3.3 cm of hand/foot position deviation while matching their orientations; the normal root margin is 4 cm. Kimodo without a curve matched the tested end-effector positions within 0.000001 m. These fixture measurements do not establish general accuracy for all poses or prompts.

MotionBricks accepts full-body pose targets only. Its keys default to FB. A partial annotation produces an explicit instruction to change it to Full Body or use Kimodo/ARDY; it is never silently reinterpreted as a full-body target.

## Ownership and persistence

Since v0.25.0, the dedicated **Keyframes** row can directly select, move and delete these native pose-time groups. The complete annotation follows each move and is removed with the key. See [pose timeline controls](TIMELINE_POSE_EDITING.md).

Non-default types are stored on the authoring Action, scoped to its Action slot. They are metadata, not another pose collection. Native key times are the only source of target frames. Annotations follow ordinary selected-key moves, including crossing/sorting existing keys. Removing the native key prunes its annotation; inserting a fresh key at that deleted frame defaults to FB. On split/merge edits, remaining keys retain their annotation and an existing destination annotation takes priority. Timers synchronize metadata outside draw callbacks, and save-pre synchronization persists it. Save/reopen and native Undo/Redo are tested. Changing keys/types while a request is pending stops further submission or skips stale completed intervals.

Existing single-type metadata remains readable. Multi-type annotations use a canonical joined token (for example `LEFT_HAND+RIGHT_HAND`), while the request expands it into separate ordinary targets at the same frame from one composed pose sample. The v0.23.0 combination update needed no companion restart; the v0.26.0 heading option requires the updated companion. The v0.22.1 partial-target FK-pop correction applies to combinations too; only an FB annotation restores exact authored local channels. Existing model limits on targets still apply.

## Validation

- `results/blender_bridge/root_height_conditions_kimodo.json` and `root_height_conditions_ardy.json`: actual native condition writers set root XYZ, optional heading and Kimodo's required Hips position, without masking other joints or any rotations. Native crop/time-shift/device/empty-segment handling preserves height targets.
- `results/blender_bridge/root_height.json` and `root_height_installed.json`: real sidebar/dialog controls, GPU R3/R3H labels, independent options, old metadata compatibility, compound goals, strict protocol/capability validation, stale-request rejection, source-key preservation, move/delete/reinsert, Undo/Redo and save/reopen. The installed run compares deployed files with source.
- `results/blender_bridge/root_height_generation.json`: real Kimodo/ARDY generation from the same saved input scene, with height/heading and a path whose elevation differs from keyed height. An identical request with height disabled provides the control. Height errors, control results and native NLA replay errors are recorded per key. `within_5cm` / `height_accuracy_status` report the separate quality criterion, including failure; `status: passed` means integration and preservation passed, not that height was accurately matched. Results are fixture-specific.
- `root_height_accuracy_hips.json` and `root_height_accuracy_raw.json` preserve the failed 5 cm accuracy runs. `root_height_probe.json` and `root_height_probe_stronger.json` record guidance probes: at high strengths the tested outputs could overshoot the requested height or alter other target heights substantially. These are diagnostic evidence, not recommended universal settings.

- `results/blender_bridge/root_heading.json` and `root_heading_installed.json`: default-off behavior, real sidebar/dialog properties, compound types, strict protocol validation, obsolete request/companion rejection, source-key preservation, move/delete/reinsert, Undo/Redo and save/reopen. The installed run also compares source and installed addon files.
- `results/blender_bridge/root_heading_generation.json`: real Kimodo/ARDY output heading measurements and native NLA replay with an independent root curve, 30/10 denoising steps and postprocessing enabled. The tested 90-degree turn reached a maximum heading deviation of 0.794 degrees in Kimodo and 4.736 degrees in ARDY. Native replay matched the raw partial-frame rotations within 0.001 radians. Measurements apply to the recorded fixture only.

- `results/blender_bridge/pose_constraint_ui.json`: real Blender property/operator calls, synthetic right-click hit/menu events, actual GPU label drawing, default/full requests, MotionBricks rejection, native moves/deletion/reinsertion, save/reopen and Undo/Redo.
- `results/blender_bridge/pose_constraint_generation.json`: actual Kimodo and ARDY requests mixing all six types in one block, generated hand/foot positions and orientations, root-curve combination, native NLA application, preserved source keys/Action/slot and one SOMA/playback track.
- `results/blender_bridge/multi_constraint_generation.json`: actual v0.23.0 Kimodo and ARDY jobs using LH+RH, LH+RF, four endpoints and LH+R2 at the same frames. Native playback at partial frames matches the raw model rotations (measured maximum 0 rad). The Kimodo fixture's maximum endpoint position error was 0.000031 m; ARDY with a curve reached 0.032564 m, within the existing 4 cm root margin. Both fixtures matched endpoint orientations. These measurements are fixture-specific.
- The updated `pose_constraint_ui.json` also covers real multi-select properties/dialog execution, FB exclusivity, canonical combined request expansion, stale-request rejection, combined GPU labels, native moves, deletion/reinsertion, save/reopen and Undo/Redo. `layered_corrections.json` retains the FB/local-key and correction-layer regression coverage.

All checks use separate background Blender instances. The user's GUI was not automated; manual layout/interaction acceptance and general motion quality remain separate from successful numerical tests.
