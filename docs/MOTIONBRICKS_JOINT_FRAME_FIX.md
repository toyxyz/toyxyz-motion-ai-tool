# MotionBricks joint-frame correction (v0.16.2)

Date: 2026-11-07. Environment: native Windows, Blender 5.2.3 LTS, RTX 5090, official MotionBricks SOMA FP32 TensorRT engine.

## Confirmed cause

The bridge constructed a SOMA skeleton from Kimodo's canonical neutral joint positions, with identity neutral rotations. It sent those local rotation deltas directly to MotionBricks. The official MotionBricks SOMA USD skeleton uses different local joint coordinate frames, including large reference rotations at the pelvis, shoulders and legs. Matching 77 joint names and hierarchy did not make the rotation representations compatible.

This produced inconsistent conditioning: the joint positions represented the intended pose, but rotation features used the wrong joint axes. The engine's endpoint post-processing still matched the first/last pose, which let endpoint-only checks pass while the intermediate motion had large joint rotation jumps. Earlier successful endpoint/application tests did not establish motion quality and missed this representation error.

The model weights, FP32 precision and text-encoder profiles were not changed by this fix. MotionBricks has no text-encoder input. The initial official example used native joint frames throughout and therefore did not have this bridge conversion error.

## Correction

`runtime/motionbricks_soma_adapter.py` loads the shipped official USD reference rotations and accumulates each joint's global reference basis. For canonical local rotation `L`, joint reference basis `B`, and parent basis `P`, the native local rotation is `P^T L B`; conversion back is `P L_native B^T`. The root's parent basis is identity. Bone offsets are expressed in the parent's native basis as well, preserving the shared canonical body proportions and world-space FK positions.

The worker converts all context/history and target-window poses before inference, then converts every returned local rotation back before resampling, continuity history and Blender application. The conversion is cached with the resident model. Results identify the path with `soma_frame_adapter: native_usd_joint_frames_v1`. The shared SOMA Blender armature and user Action remain in their existing canonical coordinate system.

## Remaining differences from the original demo

The official walking example conditions on four moving context poses and four moving target poses. An authored two-pose transition may begin from a held pose and use one final target to request a stop. The bridge also resamples model output to authored key timing. These are intentionally different inputs and can change the motion even after the joint-frame correction. Very compressed timing, unusual poses and foot contacts still require manual quality review. Numerical equivalence and successful application do not guarantee natural motion for arbitrary user poses.

Existing generated clips are not rewritten automatically. Regenerate affected blocks to replace results produced with the old rotation representation. New workers load the corrected runtime; the development companion was exercised with the corrected path during validation.
